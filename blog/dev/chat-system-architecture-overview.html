채팅 시스템 구현기 0편 - 전체 구조

2026년 11월 24일 · 약 8분
Yohan
Backend Developer

채팅방은 여러 개이고 소켓 서버도 여러 대입니다. 같은 방에 있는 두 사람이 서로 다른 서버에 붙어 있어도 메시지는 같은 순서로 보여야 합니다. 채팅 시스템을 처음부터 끝까지 만들면서 가장 먼저 풀어야 했던 문제가 이것이었습니다.

구현을 마치고 운영까지 거친 뒤에 돌아보는 기록입니다. 한 편에 다 담기에는 길어서 7편으로 나눴고, 전체 목차는 글 끝에 있습니다.

이 글은 전체 그림만 다룹니다. 메시지 한 건이 어떤 경로로 흐르는지, 왜 그렇게 나눴는지, 그 대가로 무엇을 떠안았는지까지입니다.

메시지 한 건이 지나가는 길​

시스템은 두 프로젝트로 이루어져 있습니다. 클라이언트와 웹소켓 연결을 유지하는 소켓 서버(STOMP)와, Kafka에서 메시지를 꺼내 저장하는 컨슈머입니다.

그림의 번호를 따라가면 이렇습니다.

순서누가무엇을
①클라이언트방에 메시지를 SEND 합니다.
②소켓 서버메시지를 검증하고 eventId(UUID)를 붙여 Kafka에 발행합니다. 메시지 키는 방 번호입니다.
③컨슈머파티션에 쌓인 순서대로 꺼내고, eventId로 중복을 걸러 냅니다.
④컨슈머DB에 저장하면서 방별 순번(seq)을 매깁니다.
⑤컨슈머Redis의 최근 메시지 창에 적재합니다.
⑥컨슈머방 채널로 PUBLISH 합니다.
⑦모든 소켓 서버채널을 구독하고 있다가 메시지를 받습니다.
⑧모든 소켓 서버자기에게 붙은 클라이언트의 /topic/chat/{방 번호}로 내보냅니다.

눈여겨볼 곳은 ②와 ⑦ 사이입니다. 메시지를 받은 소켓 서버는 그 메시지를 방에 바로 뿌리지 않습니다. Kafka로 보내기만 하고, 자기가 받은 메시지도 다른 서버와 똑같이 Redis를 거쳐 돌려받습니다.

저장하는 길과 전달하는 길을 나눈 이유​

메시지가 저장되는 길과 방 사람들에게 전달되는 길이 다릅니다. 지난 메시지를 불러오는 조회는 또 다른 길로 갑니다.

길경로그림의 번호
저장클라이언트 → 소켓 서버 → Kafka → 컨슈머 → DB, Redis 최근창① ~ ⑤
전달컨슈머 → Redis Pub/Sub → 모든 소켓 서버 → 클라이언트⑥ ~ ⑧
조회클라이언트 → 소켓 서버 → Redis → (캐시에 없으면) DB그림에 없음

소켓 서버가 받은 메시지를 DB에 직접 저장하고 바로 뿌리는 편이 단순하긴 합니다. 그렇게 하지 않은 이유는 연결을 유지하는 서버와 메시지를 처리하는 서버를 따로 관리하고 싶었기 때문입니다. 소켓 서버는 연결을 붙들고 메시지를 중계하는 일만 합니다. 저장, 순번 채번, 캐시 적재는 컨슈머가 맡습니다. 소켓 서버에는 채팅 메시지를 DB에 쓰는 코드가 없습니다.

순서 문제도 이 구조에서 풀립니다. 소켓 서버가 각자 저장하고 각자 뿌리면, 같은 방의 메시지 두 건이 서로 다른 서버에 거의 동시에 도착했을 때 어느 쪽이 먼저인지 정해 줄 곳이 없습니다. 방 번호를 Kafka 키로 쓰면 같은 방의 메시지는 한 파티션에 모이고, 그 파티션을 읽는 컨슈머 하나가 순서를 정합니다. Kafka 소개 문서에 따르면 키가 같은 이벤트는 같은 파티션에 기록되고, 컨슈머는 파티션에 기록된 순서 그대로 읽습니다.

KafkaEventPublisher.java
@Override
public void publishChatMessage(long roomId, ChatEvent event) {
    publish(chatMessageTopic, String.valueOf(roomId), event);
}

대가도 있습니다. 메시지 한 건이 화면에 뜨기까지 Kafka, DB, Redis를 모두 지나야 합니다. 보낸 사람조차 자기 메시지를 이 경로로 돌려받으므로, 중간 어디가 느려지면 채팅 전체가 느려집니다. 순서를 어디까지 보장하는지는 1편에서, 이 경로의 지연을 줄인 과정은 3편에서 다룹니다.

DB와 Redis를 나눠 둔 이유​

흐름을 보면 컨슈머가 메시지 한 건을 DB에도 쓰고(④) Redis에도 씁니다(⑤). 저장소를 두 곳에 둔 것은 역할이 다르기 때문입니다.

DB는 원본입니다. 모든 메시지를 영구 보관하고, 방별 seq를 매기는 곳도 DB입니다. Redis는 조회용 캐시입니다. 방에 들어오는 사람은 누구나 최근 메시지부터 불러오고, 위로 올리면 그 이전 이력을 구간 단위로 불러옵니다. 같은 데이터를 매번 DB에서 읽지 않도록 최근 메시지와 이력 구간을 Redis에 캐싱해 관리합니다.

캐싱하는 것키채우는 쪽
방의 최근 메시지 100건chat:{방 번호}:msgs (ZSET, score = seq)컨슈머가 저장 직후 적재
아티스트 메시지의 최근창chat:{방 번호}:artist:msgs컨슈머가 저장 직후 적재
그 이전 이력 구간chat:{방 번호}:seg:{n}소켓 서버가 조회할 때 DB에서 읽어 채움

최근 메시지는 쓰는 순간 컨슈머가 바로 넣고, 지난 이력은 누군가 처음 조회할 때 채우는(cache-aside) 방식입니다. 어느 쪽이든 Redis가 비면 DB에서 다시 채울 수 있어서, Redis는 날아가도 되는 보조 저장소로 다룹니다. 이 전제가 뒤에서 "Redis 실패는 로그만 남기고 넘어간다"는 실패 정책(4편)으로 이어집니다.

모든 서버가 모든 방을 받는 구조​

전달하는 길은 Redis Pub/Sub입니다. 컨슈머는 방마다 chat:{방 번호} 채널로 발행하고, 소켓 서버는 chat:* 패턴 하나로 전부 구독합니다.

RedisSubscriberConfig.java
RedisMessageListenerContainer container = new RedisMessageListenerContainer();
container.setConnectionFactory(connectionFactory);
// SyncTaskExecutor: 구독 스레드가 도착 순서대로 리스너를 호출해야 방 내 순서가 유지된다.
// (무거운 처리는 각 리스너가 워커로 넘긴다 — 여기서 붙잡히면 읽기가 멈춘다)
container.setTaskExecutor(new SyncTaskExecutor());
container.addMessageListener(chatSubscriber, new PatternTopic("chat:*"));
// ...

소켓 서버는 어느 방의 사용자가 자기에게 붙어 있는지 따지지 않고 모든 방의 메시지를 받습니다. 그래서 사용자가 어느 서버에 붙든 같은 메시지를 받고, 서버를 늘릴 때 방을 서버에 배정하는 라우팅을 만들 필요가 없습니다. 재연결하면서 다른 서버로 옮겨 가도 달라지는 것이 없습니다.

반대로 잃는 것도 분명합니다. 서버가 M대면 메시지 한 건이 Redis에서 M번 나갑니다. 자기에게 그 방 사용자가 한 명도 없는 서버도 메시지를 받아서 버립니다. 방이 많아지고 서버가 늘수록 이 낭비가 커지는 구조입니다.

Pub/Sub의 성격도 감안해야 합니다. Redis 문서는 Pub/Sub의 전달 보장을 at-most-once라고 설명합니다. 구독자가 끊겨 있거나 처리하지 못한 메시지는 다시 오지 않습니다. Kafka가 지켜 준 순서와 재처리가 이 구간부터는 따라오지 않는다는 뜻입니다. 그래서 소켓 서버 안에서 방별로 순서를 다시 지키는 장치를 두었고(2편), 유실은 클라이언트가 seq가 비는 것을 보고 이력을 다시 조회해 메웁니다(4편).

Redis 샤드를 나누면 생기는 문제​

지금 채팅용 Redis는 샤드가 하나입니다. 소켓 서버와 컨슈머는 여러 대지만, Redis는 따로 떨어진 서버 하나를 모두가 같이 씁니다. 그래서 지금은 어느 방이 어느 샤드에 놓이는지 따질 일이 없습니다.

그래도 키에는 방 번호를 해시태그로 넣어 두었습니다. Redis Cluster에서는 중괄호 안쪽만 해시되므로, chat:{1001}:msgs와 chat:{1001}:seg:3처럼 한 방의 키가 전부 같은 슬롯에 모입니다. 나중에 샤드를 나누더라도 한 방의 여러 키를 한 번에 다룰 수 있게 하려는 것입니다.

대신 샤드를 나누는 순간 아주 큰 방 하나의 쓰기는 한 샤드에 몰립니다. 방을 여러 조각으로 쪼개 샤드에 나눠 싣는 방법도 생각했지만 채택하지 않았습니다. 방이 쪼개지면 방 안의 순서와 이력 조회가 같이 복잡해지기 때문입니다. 그때 꺼낼 완화책의 순서만 정해 두었고, 앞 단계로 버티지 못하면 다음 단계를 꺼냅니다.

  1. 방별 rate-limit
  2. 브로드캐스트 샘플링
  3. 읽기 레플리카
  4. 부하 셰딩

샤드가 하나인 지금은 필요하지 않아서, 아직 적용한 것은 없습니다.

클라이언트가 받는 메시지 모양​

규격서는 공개하지 않으므로, 채팅 메시지가 어떤 모양으로 내려가는지만 보겠습니다.

{
  "frameType": "MESSAGE",
  "seqStart": 1041,
  "seqEnd": 1043,
  "messages": [
    { "eventId": "0b9f6c1e-...", "seq": 1041, "body": "..." },
    { "eventId": "5d2a77c0-...", "seq": 1042, "body": "..." },
    { "eventId": "c81e4f93-...", "seq": 1043, "body": "..." }
  ]
}

채팅 메시지는 한 건이어도 항상 이런 봉투에 담겨 내려갑니다. 뒤 편에서 계속 나올 값은 세 가지입니다.

값누가 붙이나어디에 쓰나
eventId소켓 서버중복을 거릅니다.
seq컨슈머 (DB 저장 시)방 안에서 메시지의 순번입니다.
seqStart, seqEnd컨슈머 (발행 시)봉투가 담은 순번의 범위입니다.

클라이언트는 직전 봉투의 seqEnd와 이번 봉투의 seqStart 사이가 비면 메시지를 놓쳤다고 판단합니다.

운영에서 본 숫자​

운영 중 진행한 이벤트 가운데 하나를 골라, 그 2시간 동안의 지표를 정리했습니다.

항목값
구성소켓 서버 3대, 컨슈머 2대, 채팅 토픽 파티션 1개
동시 STOMP 세션 최대3,766 (서버당 1,235~1,274)
2시간 동안 저장한 메시지약 47,300건
가장 큰 방 하나의 비중약 45,800건 (97%)
초당 저장 건수 최대28.6건 (1분 평균), 18.7건 (5분 평균)
Kafka 발행부터 컨슈머 처리 시작까지평균 6.7ms, 관측 최대 29ms
소켓 서버 브로드캐스트 큐 거부0건

숫자를 읽을 때 주의할 점이 있습니다. 세션 수는 연결 수이지 사용자 수가 아닙니다. 채팅 토픽은 파티션이 1개라서, 이 2시간 동안 채팅 메시지는 컨슈머 2대 가운데 1대가 모두 처리했습니다. 다른 1대는 채팅 토픽의 파티션을 받지 않았고, 처리하던 쪽이 빠지면 그때 파티션을 넘겨받습니다. 지연은 Kafka에 발행한 시각부터 컨슈머가 처리를 시작한 시각까지만 잰 값이고, 클라이언트가 보내서 받기까지의 지연은 운영에서 재지 않았습니다. 그 구간은 6편의 부하테스트에서 따로 쟀습니다.

메시지의 97%가 한 방에서 나왔다는 점도 적어 둘 만합니다. 샤드를 나누면 큰 방 하나가 한 샤드에 몰린다고 앞에서 적었는데, 실제 부하도 그런 모양이었습니다. 다만 지금은 샤드가 하나이고 초당 30건 미만이라 문제가 되지 않았습니다.

돌아보며​

이 구조에서 판단의 기준은 하나였습니다. 순서를 정하는 곳을 한 군데로 모으는 것입니다. 소켓 서버가 몇 대든 같은 방의 메시지는 한 파티션, 한 컨슈머 스레드를 지나며 순번을 받습니다. 나머지 결정은 대부분 여기서 따라 나왔습니다. 소켓 서버가 직접 에코하지 않는 것도, 모든 서버가 모든 방을 구독하는 것도 그렇습니다.

떠안은 것도 정리해 둡니다.

  • 메시지 한 건이 거치는 구간이 깁니다.
  • 서버 수만큼 Redis 전송이 늡니다.
  • Pub/Sub 구간은 유실될 수 있습니다.
  • Redis 샤드를 나누면 큰 방이 한 샤드에 몰립니다.

이 가운데 앞의 세 가지는 뒤 편에서 하나씩 다룹니다.
